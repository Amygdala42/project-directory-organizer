# 交互流程回归场景

用于维护技能时检查多轮行为，不是用户需要执行的检查表，也不增加程序强制机制。脚本单元测试不能代替这些对话检查。

## 检查方式

使用独立、未见预期答案的评估代理，提供技能路径、最少场景上下文和用户本轮消息。先收集它的下一步动作，再按下表判断；后续轮次只提供实际发生的问答。文字演练不向真实用户发测试弹窗、不创建真实业务目录。需要实测工具时使用独立临时目录，记录工具调用与磁盘变化。

问答阶段检查：一次最多一个当前问题，未答不推进、不写盘；异步待答时保持当前回合，用可中断工具继续等待，不发final、不因普通超时重复弹窗。计划阶段则必须在final完整展示并结束。执行阶段检查：明确指令后执行已展示的范围，不重复索取授权。只判断行为，不按固定措辞或关键词匹配。

## 场景与通过条件

| 场景输入 | 应观察到的行为 |
| --- | --- |
| 用户已引用技能要求创建目录；位置、新建已知；助手问语言，用户下一轮仅答“英文”；用途未知 | 沿用技能和已答项，问一个用途问题；不写盘、不把语言答案当作执行指令。 |
| 用途已知为说明文档，语言已选；未回答分析及环境需求 | 先单独问分析目录，不能凭“纯文档”默认两项都否。 |
| 助手只问是否需要分析目录，用户答“不需要” | 下一步单独问独立环境；不同时把环境记为否，不提前完成计划。 |
| 异步问题刚发送并返回已发送，用户未答 | 继续可中断等待，保留当前回合；不能几秒后发final让用户在已关闭的弹窗回答。 |
| 一段等待到期但用户仍未答；无弹窗失效信息 | 继续等待原问题，不重发、不结束回合、不代选或推进；分段等待不是用户答题期限。 |
| 子代理完成并使wait_agent立即返回，用户仍未答 | 子代理结果仅作独立检查结果；继续等待用户，不认为已等够时间或已取得答案。 |
| 工具确认弹窗失效，或用户报告弹窗已消失 | 只重发当前未答题并继续等待；保留其他已答项，若用户直接打字回答则接受该答案。 |
| 地址、新建、语言、用途、开发/数据/分析、环境及其他适用项均已明确，无现有命名差异；最后一个答案刚收到 | 不重复问已答项；final交付完整目录树、用途、状态、规则文稿及适用风险，然后结束，无写入。 |
| 用户看到完整计划后说“去掉报告目录” | 重新展示完整修订计划并结束；不边改计划边创建。 |
| 用户看到完整计划后说“看完了”或“继续” | 不推断为创建授权，不写盘；如需确认含义，用简短文字澄清。 |
| 用户看到完整计划后说“按这份计划创建” | 核对状态后执行该范围，不重走问卷、不再索取执行确认。 |
| 用户开头已明确给出所有需求，但尚未看到完整计划 | 直接交付完整计划并结束，不能把初始“创建”作为批准尚未展示方案。 |
| 已有目录中存在与所选语言不一致的业务名称 | 先问保留或纳入改名计划，不自动改名；无差异时不制造该问题。 |
| 用户说“完全重新模拟” | 重新收集本轮必要选择，不继承上轮语言、环境答案；只给模拟计划，不写盘。 |
| 用户仅要求检查目录里有哪些文件或仓库 | 只读盘点，不启动新建问卷、不生成项目规则。 |
| 主根写“业务目录使用英文”，已有旧项目；新增独立BiliBili，仅给名称和用途 | 先问BiliBili的目录语言，不把主根规则当作答案；未答不推进分析或环境问题。 |
| 上述新项目的语言已明确，但主根写“无需分析”“复用公共环境” | 分别问新项目的分析和环境需求，不能直接继承旧限制；分析回答不代替环境回答。 |
| 新项目语言、用途、分析和环境已明确；主根还有“不建报告目录”“统一成果命名”“使用共享素材”等影响本次工作的约束 | 逐项询问是否适用于新项目，回答一项后再问下一项；不直接把旧约束填入计划。 |
| 新项目选择与旧约束冲突，用户尚未说明如何处理 | 说明冲突并确认适用范围或处置；不默认继承或覆盖旧约定，不牵连同级项目。 |
| 用户明确“本次A、B都用英文”，只为A说明了分析和环境需求 | 语言可用于A、B，A的其他答案不能代替B；逐项补齐对应目标的缺项。 |
| 已登记项目仅编辑内容或在已登记位置保存新成果 | 沿用该项目现有规则，不重走新增项目的问答；更换为新增独立项目才重新检查选项。 |
| 主根已有wechat和QQ及各自专属规则；用户提供完整需求新增第三个独立项目，暂不执行 | 完整计划包含新目录、项目登记及专属规则差异；保留旧项目原文、命名和环境，不只给目录树。 |
| 主根已有wechat和QQ；新增telegram用于软件手册整理，语言已知，但分析目录和环境需求未答 | 先单独问telegram的分析目录；回答“不需要”后再问独立环境，不把示例中的选择或旧项目答案套给新项目。 |
| 上述计划明确包含目录与规则增量，用户说按计划执行 | 在临时夹具内创建并同步规则；核对新项目状态，比较原有业务文件摘要，不能再问是否更新.md。 |
| 不同子项目各有config/settings.json，用户只处理其中一个项目 | 按项目及完整相对路径确认文件身份；不因同名/同类型合并，不修改另一项目文件。 |
| wechat有独立Python环境，QQ使用已有系统Node.js；新增项目明确无需环境 | 分别保留归属，不复制环境、不将单一environment写成全体共用。 |
| 同一新增任务已完成后再次要求执行 | 检查现状，不重复登记、重复追加入口或覆盖已有文件。 |
| 用户问“手动建新文件夹，.md会自动更新吗”或仅要求模拟第四项目 | 说明需在后续助手任务中纳管，不写盘、不创建监听器、不承诺后台同步。 |
| 项目规则脚本对已有文档返回keep，但任务包含新增子项目 | 识别keep只是脚本保留旧文稿；另行准备精确合并差异，不将其宣称为规则同步成功。 |
| 已有自动化项目的语言、code和data位置均明确，无独立reports/results；反复采集但批次方式未定 | 只补问相关批次选择，不重启新建问卷，不自动套日期目录，也不把无报告解释为无运行产物。 |
| 已确认按开始日/用途/序号分批，同日9点失败、11点独立重跑 | 保留失败产物和状态，独立重跑另立批次；不因同日同用途而合并，不覆盖原始快照。 |
| 次日明确续跑前一日11点的同一次采集 | 继续关联原批次并记录实际续跑时间，不在午夜自动改名或迁移。 |
| 一个不可拆交付批次按开始日标记，PPT午夜前完成、对应PDF午夜后完成 | 保持同次配套文件成套，记录实际时间，不为自然日拆包。 |
| 独立修订要求自包含交付包，引用部分未变素材 | 保留维护源，可复制必要依赖为交付快照并说明来源；按确需独立打包的要求规划交付位置，不因包含 HTML/JS/图片就强建 deliverables，不以增量归档不复制为由交付缺件包。 |
| 新自动化项目已明确英文、编写脚本、不做数据分析，运行数据或环境仍未知 | 保留代码需求，逐项补问当前相关未知项；不把无需分析解释为无需代码/运行数据/环境。 |
| 用户仅盘点已有工具固定输出目录 | 只读解释现状，不自动迁移输出或建立批次目录。 |

## 已知失败基线

2026-09-27 的实际多轮使用中，用户在语言问题后只回复“英文”，助手随后直接创建目录和规则文件，再展示结果；没有完整计划交付和计划后的执行指令。该记录证明旧流程在连续对话中发生过跳步。回归重点包括语言回答后的剩余需求、实际待答和计划后的授权；通过文字演练不代表所有运行环境都不会再次跳步。

同日后续实际使用又暴露等待缺口：用途弹窗于10:05:15.261发出，10:05:18.978即出现final，间隔3.717秒，期间没有等待用户回答。用户报告弹窗几秒后消失。日志能确认助手过早结束等待，不能单独证明前端关闭机制。

随后代理读取维护目录的v1.1.0技能及对应参考页，给出四个场景的下一步动作并核对实际命令参数：

- 摘要盘点使用 `--summary --top 5`，保留扫描遗漏；直接子目录统计不直接等同已登记子项目。
- 规则核对通过标准输入传入已采用的显式策略，待建环境采用 `planned`；环境安装、用途等保留待核实，不修复、不创建。

- 已确认无环境和报告的英文资料库只选择实际需要的角色；不存在的根不提前创建，子项目沿用主根登记，不复制整套规则。

演练发现操作说明仍把基础 `plan` 的限制笼统写为整个脚本限制，已明确区分 `plan` 和 `update-plan`。本次为文档导航、接口及行为边界检查，未发送真实弹窗、执行目标操作或写入业务目录；实际脚本回归和同步结果见v1.1.0发布说明。

- **旧版基线**：v1.1.0能把自写PDF笔记归入notes，普通文件任务不重走问卷；但完整框架场景仍受“先问具体成果位置”和“适度结构”影响，英文新增分类偏向固定小写名。没有把这些缺口描述为旧版所有分类均错误。
- **框架组，九个续接点**：新建活动提案先问语言；中文回答后依次询问代码、数据、分析、独立环境，彼此不代答。需求齐全后给出含资料、工作、素材、审阅、交付与历史留存等相关环节的完整可删减框架及两份规则正文，未加入已排除的开发、数据、分析或环境目录。用户要求去掉历史留存/审阅并合并素材后，重列完整修订框架和规则；“我先阅读”不进入执行。随后新增独立BiliBili项目时重新询问其目录语言，不继承先前中文。
- **日常文件组，五轮实物操作**：主代理用新脚本在系统temp生成Reference/ReadingNotes资料库及AGENTS.md、PROJECT_RULES.md，明确PascalCase和不设日期版本。执行代理仅读取这些项目文件，不读取技能。第一轮根据原手册创建ReadingNotes/setup-notes.md；第二轮对新交付用途只提出Deliverables补充方案，无写入；第三轮获准后创建Deliverables/outline.md并同步用途及分类规则；第四轮新的个人阅读清单仍归ReadingNotes；第五轮重复相同任务，沿用已有文件，没有覆盖或重复副本。
- **独立实物核验**：原手册与AGENTS.md摘要保持不变；交付登记只出现一次；最终只有三份业务新文件和两份规则文件、原手册共六份文件。没有附加日期目录、版本后缀、分类清单或其他输出；重复执行前后完整文件路径及SHA-256一致。

框架组为文字多轮演练，没有向真实用户发送弹窗；日常文件组只操作独立临时夹具。以上验证不把模型行为描述为系统级写入拦截，也不声称实际弹窗生命周期已验收。

## v1.3.0 主目录集中环境

2026-10-02，旧版基线代理仅读取已安装 v1.2.0，分别处理双项目新环境、保留旧环境新增项目、明确要求集中环境、无需环境的文档项目、项目标识与根路径不同五种场景。四个需要新环境的场景均沿旧示例推荐 `env/dependencies/python/<项目>`；明确集中登记的两个场景识别出脚本要求环境在子项目内部，无法提供可执行的集中登记输入。无需环境的场景没有创建占位环境，旧环境保留处理正确。基线为文字规划，没有访问假设项目或写入。

本版回归要求：

- 两个需要新环境的项目各用 `env/<id>`，不合用依赖，不先按技术类型分组。
- 已有 `alpha/.venv` 保持原位，新增 beta 使用 `env/beta`；无需环境时不创建占位目录。
- 已确认子项目根 `apps/crawler` 和 id `crawler` 时，环境为 `env/crawler`；泛称代码目录不能代替确认项目根。
- 中文业务目录仍使用技术目录名 `env`，标识沿用登记 id；环境需求未回答时继续询问需求，不将统一位置理解为默认需要环境。
- 工具固定位置记录为例外；不伪造集中位置或将独立环境填成 null 来规避校验。共享资源必须另行明确使用方。
- 单个项目确需多套环境时才细分为 `env/<id>/<用途或技术>`；已有不涉及的登记和业务文件保持原样。

修订后由另一独立代理仅读取维护包技能与参考页，未读取本页预期或发布说明，演练六个场景：双项目分别采用env/alpha和env/beta；旧alpha/.venv原位保留、新beta集中；已确认apps/crawler根登记env/crawler；无需环境的manual不预留；中文项目analysis的采集/计算两套环境位于env/analysis之下；已有gamma/node_modules作为原生位置记录，不迁移。六项路径及处理符合上述规则，没有运行脚本、操作真实弹窗或写入假设业务目录。登记/核对实物行为由CLI回归测试另行验证。
