# Project Directory Organizer

适用版本：**v1.4.1**。变更见[本版记录](releases/v1.4.1.md)。

本版增加多项目管理方式必答项，修复移动回退日志硬链接保护、项目登记转义引用识别及 Markdown 链接核对，并精简维护职责与重复说明。

## 获取与维护

从 [v1.4.1 Release](https://github.com/Amygdala42/project-directory-organizer/releases/tag/v1.4.1) 获取发布文件：普通使用选择[技能包](https://github.com/Amygdala42/project-directory-organizer/releases/download/v1.4.1/project-directory-organizer-skill-v1.4.1.zip)，修改源码和执行开发测试选择[维护包](https://github.com/Amygdala42/project-directory-organizer/releases/download/v1.4.1/project-directory-organizer-maintenance-v1.4.1.zip)。两者解压后的顶层目录均名为project-directory-organizer，但内容不同：技能包直接包含SKILL.md、agents、assets、references和scripts；维护包还包含README、VERSION、docs、tests，技能位于其中的skills/project-directory-organizer。

持续维护以仓库中的技能目录为唯一维护源，再将已验证的同版内容同步到安装副本。核对版本后，还需比较全部相对路径与文件SHA-256；本版技能包包含20个文件。维护仓库根的AGENTS.md和PROJECT_RULES.md用于维护本仓库，技能内assets/templates中的同名文件用于生成目标项目规则，二者职责不同。

下载后可将ZIP的SHA-256与同版 [SHA256SUMS.txt](https://github.com/Amygdala42/project-directory-organizer/releases/download/v1.4.1/SHA256SUMS.txt) 比较。发布包对应固定标签快照，维护分支继续更新；校验值与验证范围集中记录在[发布状态与校验](releases/v1.4.1.md#发布状态与校验)。

## 使用方式

计划前按顺序用简短弹窗收集信息：位置 → 新建或整理 →（多个独立项目适用）管理方式 → 目录语言 →（存在差异时）现有名称如何处理 →（用途不明时）补问用途 →（新建任务）逐项确认未明的代码、运行数据和分析成果需求 →（新建任务）独立环境 → 其他影响本次工作的选项或旧约束。用途问题只问缺失信息，不要求正式主题名称。不做数据分析不等于不需要代码、运行数据或环境；已明确的需求不重问，相关未知项每次只问一个。只读盘点已知范围内的内容不触发新建问卷。

管理方式与目录语言同为适用时的必答项。涉及多个独立项目且方式未明确时，单独询问：“这些项目需要在同一个工作区统一管理，还是分别打开、各自独立维护？”已有明确答案或明确覆盖目标的管理约定不重问；不能只凭共同父目录或 AGENTS.md 的存在推断选择。单项目和 src/docs 等同一项目的功能目录跳过此题。未回答时，不完成依赖该选择的规则布局和路径安排。

同一目标的后续轮次继续本技能，无需重复引用，沿用明确覆盖该目标的答案，不重问；新增独立项目重新检查全部前置选项及会影响本次工作的约束。主根或旧项目的语言、用途、分析、环境、成果、命名归档和共享安排不能替新项目作答，相关未知项逐一询问；用户明确覆盖本次多个目标的选择可复用。用户要求完全重新模拟时，重新收集本轮必要选择，不继承上轮答案。每次只问一个问题，必须等到用户实际回答后才能提出下一个；默认值、超时或沉默都不算回答。重发只补问当前待答项。用户回答单项问题只更新对应信息，不代表授权创建。不因目录名或自行判断“纯文档”而略过分析和环境确认。

异步弹窗发出后，助手保持当前回合，分段等待实际回答，不在几秒后用结束回复催用户操作。每段等待不超过60秒，未答继续等待；这不是用户的答题期限。只有工具报告失效或用户反馈弹窗消失时才重发当前题，不因普通超时重复弹窗。直接打字回答当前问题也有效；技能不控制应用自身的弹窗显示时长。

必要信息齐全后，推荐任务相关、较完整的候选框架供删减，具体名称和层级不再逐目录提问。在正式回复中一次性给出完整计划，包括目录树与用途、已存在和待建内容，以及规则文件的完整正文或相对现有文件的差异；随后结束并等待文字指令。规划阶段不写文件。用户可删减、合并、改名，修订计划时同样完整展示，不弹窗或追加执行确认。树中拟建项是当前执行范围，待定建议单列；从计划删掉候选不表示实际删除已有目录。用户明确要求改变流程时，按其要求处理。

## 何时实际操作

用户明确说“按这个计划创建”“执行上述移动”“保存这份方案”等，才执行对应范围，不额外问一遍确认。已有授权仅覆盖已展示的具体范围；已有明确具体的操作指令继续有效。初始泛泛的“创建 X 目录”是规划目标，不代表批准未来尚未展示的布局。只有修改意见、认可结构、模糊的“继续”或沉默，不当成真实写入指令。模拟不会因方案通过而自动变成实际创建。

发现范围扩大、冲突或新风险时，停止受影响项并给出更新计划。脚本的--confirm、摘要和日志绑定继续保留，它们是技术校验，不是交互问卷。

## 目录与规则

根据用途、查找方式和现有结构推荐目录。第一版可覆盖资料、工作、素材、审阅、交付和记录等相关环节，标明建议保留与可删减扩展；开发、数据与分析位置按各自答案选择；新建且可自由定位的独立环境统一放在已确认主根的 `env/<项目标识>/`，已有环境和工具固定位置沿用。没有适用需求的候选不创建，已有工程沿用其原生结构。语言沿用本轮明确选择，未知时先弹窗询问；发现语言差异，前置弹窗确定处理意向，再在计划中列改名建议与风险，不自动改名。

实际新建时，主项目 AGENTS.md 保留规则入口、目标子项目范围和简短文件保护原则，以相对链接引用 PROJECT_RULES.md；已知的项目介绍、关键约束和简短真实进展可保留在入口，详细任务链接到对应记录，不编造最新状态。项目短规则记录实际约定、每个目录的主要内容、必要配套和应另存内容及其位置，并说明每次创建前分类、归属与规则维护、文件保护及适用的成果安排；未选择成果输出位置时省略成果归档节。只写已选布局及实际用途，目录表可在同一项目内归组；通用候选、中英映射、环境可选类型及详细操作流程留在技能中按需读取。

项目约定保留目录语言、时区和实际环境归属。中文选择覆盖当前目标的自建业务目录层级，工具要求的原生结构保留并说明；此选择不决定文档正文或文件名语言。环境预留只是位置，不代表已安装。可独立归档的报告和分析导出沿用已明确适用于当前目标的约定，日期、编号、分隔符、版本与批次层级按实际选择采用；关联材料按各自目录边界保存并保持引用。源码、设计源文件、关联素材及工具生成目录沿用原生布局，不强套日期或 v01 命名。

反复采集、处理和自动化任务另按需要确认运行批次：已有数据位置不等于已有批次约定，只补问本次相关的未定项。独立运行和失败后的独立重跑分别标识，明确续跑才复用，并保留原产物和状态；跨日续跑不在午夜自动换批。文件可按批次成套保存，也可保留稳定路径并关联运行标识，不强制新建目录或导航文件。

交付批次也不等于自然日：同日同用途的独立批次需区分，同一不可拆交付批次跨日完成时保留PPT/PDF及必要配套关系，记录实际产出时间。日常增量只保存新增/修订；确需独立打包的自包含交付件才规划 `deliverables/` 或现有布局中的对应位置，可复制必要依赖为快照并注明维护源。HTML、JS、图片等混合格式本身不是另建交付目录的理由：用于阅读同一报告的资源可随报告保存，用于生成报告的源码仍有自己的维护位置。细节与例子见[运行与交付批次](../skills/project-directory-organizer/references/directory-reference.md#5-成果与运行批次)。

弹窗、等待、重发、模拟及对话流程只保留在技能内部，不写入这两份项目规则。没有结构或规则变更时，已有定制 PROJECT_RULES.md 保持原样，不因模板更新自动覆盖、追加通用内容或要求补齐候选目录；新增项目、改变用途或用户要求修订时，在同一计划中按现有内容提出相关差异，保留其余约定。

## 项目持续维护

用户或适用规则明确采用后，将覆盖范围及实际维护路径写入 PROJECT_RULES.md，在 AGENTS.md 保留入口。没有采用时沿用现有工作流，不因安装技能创建 devlog 或补写历史记录。全局规则按适用范围遵守，项目操作不顺带改写全局配置。

项目 AGENTS.md 保存介绍、关键约束和简短真实进展，详细过程链接到任务记录；PROJECT_RULES.md 集中维护目录及工作约定。采用后，实际改动前复用或创建同一任务记录，完成或中止时回填结果、实际验证、未完成项和下一步，同步项目入口。流程覆盖新建、修改、复制、导出、整理、归档及另获授权的删除；纯只读查看与规划不写记录，记录自身及配套状态更新不递归另建记录，也不增加重复确认或扩大业务范围。

任务、笔记、工具说明、日志、暂存和历史归档按用途选用，devlog/note、tasks、tools 及其 archives 只是可选布局，已有合适位置优先复用。日志与暂存需区分职责；归档核对状态及引用，有效旧规范继续维护，保留期限不构成移动或删除授权。

本维护仓库复用 docs/superpowers/plans 记录任务及决策，docs 保存使用说明，docs/releases 保存发布记录，详细测试输出及临时产物留在系统临时目录。

升级技能不会自动升级旧项目。同步指定项目时读取实际规则，以授权范围内的精确差异合并并核对真实文件，保留手写内容及其他项目；基础 plan 返回 keep 只表示保留原文，不能证明维护条款已落地。规则通过助手执行，不提供后台监听、自动归档或系统级写入拦截。

角色边界、首次记录、前后回填、归档与旧项目升级的完整细则统一见[项目持续维护参考](../skills/project-directory-organizer/references/project-maintenance.md)。

## 每次创建文件前分类

新建、复制、下载或导出项目文件前，依次判断“项目归属 → 用途与状态 → 关联 → 位置 → 命名”。先分清材料属于哪个项目、是成品还是内部过程材料，再核对实际阅读、使用或运行关系，选择位置并沿用命名规则。扩展名可辅助识别文件，不能代替角色判断；外部 PDF 手册属于资料，Markdown 也可以是最终报告。工具生成项遵从原生路径。详见[分类方法](../skills/project-directory-organizer/references/directory-reference.md#1-文件分类与目录选择)。

这套方法覆盖所有目录。新建方案及项目规则逐目录写清主要内容、必要配套、应另存内容及其去向；生成前可按角色一次安排整批输出，不必逐文件提问。整理计划逐条核对原→新映射，整目录移动检查所有后代的用途、状态和真实关联，不能仅凭后缀或顶层目录名判定通过。完成后复核实际内容，列明保留项与未核实项。整理产生的方案、清单和日志也按自身用途安排位置。

必要配套是阅读或使用该目录主要内容所需的材料，或已经明确属于本次交付的附件。应说明其服务对象和保留关系；“同次生成”“同一项目”或笼统的“相关”不能单独成为同目录理由。以下为角色示例，路径沿用当前项目已选布局，不要求预建整套目录：

| 目录用途 | 主要内容与可保留的必要配套 | 应另存内容 |
| --- | --- | --- |
| 报告成果 | PDF、Word、PPT、Markdown 或 HTML 报告；阅读说明、必要配图及报告阅读资源；明确随报告交付的 CSV 结果表、JSON 样例、最小复现脚本及其说明 | 内部报告生成器、内部写作草稿、运行配置、中间数据、缓存和运行日志，分别放入开发、工作、数据或运行记录位置 |
| 图片成果 | 已选定的图片及使用它们所需的图注、来源或使用说明 | 作图程序、内部编辑工程、试验输出和缓存按维护或过程用途保存；报告正文归其成果位置 |
| 代码或设计工程 | 源码、设计源文件及必要的 `config.json`、README、素材和原生依赖结构 | 与工程运行或维护无关的独立资料、正式报告和历史输出按自身用途保存 |
| 数据 | 原始、处理后或已选定的数据，按状态区分；字段说明、数据字典和来源说明可随数据保存 | 数据处理程序、独立分析报告与运行日志按开发、成果或记录用途保存 |
| 资料 | 外部手册、参考材料及必要的来源、索引说明 | 自写工作草稿、项目运行配置和产出报告按工作、工程或成果用途保存 |
| 工作与草稿 | 内部草稿、备选方案、审阅材料及其配套 | 已定稿交付件、可独立维护的生成器和运行产物按对应角色保存 |
| 运行记录、缓存或临时文件 | 本次运行所需的日志、状态记录、可再生成缓存或临时材料，各按已约定用途和保留方式管理 | 维护源、原始材料和正式交付件保存在其稳定位置，不因同次运行混入 |

同一个 README 可以是报告阅读说明、工程维护说明或内部整理记录；CSV、JSON 可以是交付附件、数据集、运行配置或中间文件。明确交付的最小复现脚本可作为报告附件，内部生成器仍按开发用途保存。按真实角色处理，也不因文件名叫“附件”就视为交付。批次子目录沿用所属用途；混合格式不必另建 `deliverables/`，确需独立打包时才规划。

已有明确项目约定优先；与本次目标冲突时提出精确规则调整，不自动迁移历史文件。规则足够、任务已授权时直接创建；缺用途或归属时只问当前缺项，没有适合位置时准备最小目录与规则增量。每份材料保持明确维护位置，交付快照与维护源关联。该约定通过项目规则指导助手，本版未新增语义检查器，也不监听用户手工创建或自动拦截其他程序。

## 集中环境

仍逐项目确认是否需要独立环境；确认需要新建且位置可自由指定后，采用 `已选管理根/env/<项目标识>/`，不再反复询问主目录还是子目录。统一管理以工作区根为基准，独立维护以各项目自身根为基准；根来自明确选择，不自动向上找共同父目录。`env` 是统一技术目录名，不随业务目录语言翻译；项目标识复用已有登记 id，单项目使用自身稳定标识。只有确需多套环境时才在该项目环境目录下细分。以下为统一管理示例：

```text
主目录/
├─ env/
│  ├─ alpha/
│  └─ crawler/
├─ alpha/
└─ apps/
   └─ crawler/
```

例如已确认子项目根为 `apps/crawler`、标识为 `crawler`，登记环境使用 `env/crawler`。集中存放不意味着项目间共用依赖；共享资源须另行明确使用方。已有 `.venv`、`node_modules`、锁文件和工具固定位置保留原位并在规则中记录；新约定不授权迁移、重建或安装。不需要环境时不创建空目录；只预留时明确标记未配置。

增量登记支持 `env/<id>` 及其后代，同时保留本项目内部环境路径的兼容能力。成果路径继续严格限制在所属子项目内。校验会考虑同批及已有登记，拒绝环境重复、相互包含或侵入其他项目根；只读核对也识别集中环境，但目录存在仍不能证明环境安装成功。具体接口和例外见[多子项目管理](../skills/project-directory-organizer/references/subprojects.md)。

## 多个独立小项目

wechat、QQ 等多个独立项目先明确管理方式，不因它们位于同一父目录就默认统一管理：

| 已选方式 | 规则与路径基准 |
| --- | --- |
| 同一工作区统一管理 | 工作区根维护 AGENTS.md、PROJECT_RULES.md 和项目登记，分别记录标识、相对根、用途、状态、环境及成果约定；不向每个子项目复制同一套规则，保留已有工程内部规则。新增项目用 update-plan 增量登记。 |
| 分别打开、各自独立维护 | 每个项目根保存完整 AGENTS.md 和 PROJECT_RULES.md，能在分别打开后读取本项目约定，不仅放置指向父目录的入口。各自根为环境、成果及规则路径基准，分别运行 plan；共同父目录不建立总登记。 |

处理一个项目时不套用另一项目的约定，同名文件保持项目身份。统一环境存放不意味着共享依赖；共享项另列使用方和维护位置。管理方式问题留在技能流程中，生成的项目规则只记录已选方式及其具体约定。

新增、改名、归档或改变用途时，完整计划包含已选管理范围内的规则差异；获得该范围的执行指令后一起完成，不再为规则文件重复索取许可。普通内容更新不重写目录规则；手动创建文件夹和只读盘点不会触发后台写入。写后核对相应规则、入口及登记与磁盘一致，其他项目的专属约定和业务文件不变。完整流程见[多子项目管理](../skills/project-directory-organizer/references/subprojects.md)。

## 首次生成的布局输入

`project_rules.py plan ROOT --language english --timezone TIMEZONE --layout-file -` 从已选布局生成短规则，中文项目将语言参数改为 `chinese`。统一管理的 ROOT 为工作区根；独立维护时，对每个项目自身根分别运行。`--layout-file` 只在首次创建 PROJECT_RULES.md 时必需；助手依据用户已确认的目录计划准备，不增加用户问题或 JSON 表单。`-` 表示经标准输入传入，无需在项目中保存布局文件；也可将该参数替换为已有且获准保存的布局文件路径。

| 字段 | 内容 |
| --- | --- |
| scope | 本项目已知工作范围，使用文字字符串，不要求正式主题名称 |
| directories | 已选目录及用途，格式为 `[{"path":"相对本次ROOT路径","purpose":"用途"}]`；用途表允许按类别归组，目录边界可在 purpose 或 rules 中写明 |
| environment | 本次约定的独立环境目录相对路径，须在 directories 明列；新建且可自由定位时采用 `env/<项目标识>`。未选择时为 `null`，不表示项目没有已有环境；旧布局输入保持兼容 |
| outputs | 明确选定的报告或导出归档位置相对路径列表，须在 directories 明列；没有则为空列表。不要把 build/dist 等工具生成目录或关联源码素材作为归档位置 |
| originals | 已确认原件的项目相对路径列表，可为目录或文件（如根内 contract.pdf），不要求包含在目录用途表中 |
| rules（可选） | 已确认的具体分类、命名、批次或已采用的持续维护约定列表，可写明任务记录路径及维护流程；最多500条单行文本，每条最多1000字符，拒绝控制字符及内部保留标记；省略或空列表不补设业务约定 |

`TIMEZONE` 替换为已知项目约定或当前会话的时区；没有固定地区默认值。助手从已有上下文取得，不为此增加常规问卷；确实无法确定时先在计划中标为待定，不编造时区。

上述首次生成布局只有一个environment字段，基础plan保留已有PROJECT_RULES.md。统一管理需要增量登记时，使用 `project_rules.py update-plan ROOT --projects-file -`，逐项目提供已确认的环境和成果位置，生成schema 3局部更新计划；独立维护继续对各根分别 plan，不建立共同登记。执行仍使用原apply命令。无管理标记的旧文档需精确绑定迁移段或明确初始化锚点，人工改动和歧义返回blockers。完整字段与迁移规则见[多子项目管理](../skills/project-directory-organizer/references/subprojects.md)；基础plan的keep仍不代表已经登记新项目或升级旧规则。管理方式复用现有输入，不新增schema字段。

旧输入仍可使用；保存计划绑定当时的模板，模板升级后需重新生成并核对计划。布局是生成输入，不是新增项目隐藏设置。工具计划和摘要不构成写入授权；完整文稿仍先在正式回复中展示，实际写入遵从用户已明确的操作范围。详见[选中布局示例](../skills/project-directory-organizer/references/examples.md)。

## 盘点摘要与规则核对

大目录可运行 `folder_inventory.py ROOT --summary --top 10`，省去逐项清单但保留扫描范围、遗漏和错误，按直接子目录、扩展名和修改时间汇总，并列出完整相对路径的文件榜单。直接子目录只是分组，不自动认定为独立子项目；默认命令的完整 JSON 输出保持兼容。详见[盘点说明](../skills/project-directory-organizer/references/inventory.md)。

`directory_verify.py ROOT --policy-file -` 接收助手从已确认约定整理的检查策略，只报告路径及文件/目录类型、局部命名、规则入口链接及项目归属的符合、偏差和未核实。`names` 的 glob 只核对指定目录的直接子项名称，不递归验证文件格式，也不检查文档内容是否属于报告。计划中尚未创建不算缺失，目录存在不代表环境已安装；用途、自由条款和不完整扫描不伪装成通过。可用 `--strict` 令偏差或未核实返回非零。策略字段、正文读取限额及退出码见[只读规则核对](../skills/project-directory-organizer/references/verification.md)。

用途已明确时可使用[可裁剪的规划范例](../skills/project-directory-organizer/references/planning-recipes.md)辅助选择目录角色。范例不是创建或检查清单；已有原生结构、当前选择和真实引用关系优先。

## 整理与保护

整理先评估引用、资源完整性、外部依赖、原件、链接及目标冲突。检查通过且独立的完整组可列入移动计划；风险或未知组保留并给建议。代码、环境、原件及项目根改名不作为普通自动整理处理。

本次整理指南MD记录映射、评估、实际结果和回退入口；收到保存或执行指令后，才写入已列明的位置。执行失败停止并保留记录；完整成功且条件满足的移动批次可按明确指令回退。精确删除与恢复仍采用专门流程，不从泛泛整理推断删除。
