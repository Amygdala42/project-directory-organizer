# Project Directory Organizer

适用版本：**v1.0.1**。变更见[发布说明](releases/v1.0.1.md)。

## 使用方式

计划前按顺序用简短弹窗收集信息：位置 → 新建或整理 → 目录语言 →（存在差异时）现有名称如何处理 →（用途不明时）补问一项用途 →（新建任务）是否需要分析目录 →（新建任务）是否需要独立环境。用途问题只问缺失信息，不要求正式主题名称。分析目录和独立环境是两个分别确认的事项；无需分析不表示无需环境。只读盘点已知范围内的内容不触发新建问卷。

同一任务的后续轮次继续本技能，无需重复引用，沿用已明确答案，不重问；用户要求完全重新模拟时，重新收集本轮选择，不继承上一轮语言和环境答案。每次只问一个问题，必须等到用户实际回答后才能提出下一个；默认值、超时或沉默都不算回答。重发只补问当前待答项。用户回答语言、用途、分析或环境问题，只更新对应信息，不代表授权创建。不因目录名或自行判断“纯文档”而略过分析和环境确认。

异步弹窗发出后，助手保持当前回合，分段等待实际回答，不在几秒后用结束回复催用户操作。每段等待不超过60秒，未答继续等待；这不是用户的答题期限。只有工具报告失效或用户反馈弹窗消失时才重发当前题，不因普通超时重复弹窗。直接打字回答当前问题也有效；技能不控制应用自身的弹窗显示时长。

必要信息齐全后，在正式回复中一次性给出完整计划，包括目录树与用途、已存在和待建内容，以及规则文件的完整正文或相对现有文件的差异；随后结束并等待文字指令。规划阶段不写文件。修订计划时同样完整展示，不弹窗或追加执行确认。用户明确要求改变流程时，按其要求处理。

## 何时实际操作

用户明确说“按这个计划创建”“执行上述移动”“保存这份方案”等，才执行对应范围，不额外问一遍确认。已有授权仅覆盖已展示的具体范围；已有明确具体的操作指令继续有效。初始泛泛的“创建 X 目录”是规划目标，不代表批准未来尚未展示的布局。只有修改意见、认可结构、模糊的“继续”或沉默，不当成真实写入指令。模拟不会因方案通过而自动变成实际创建。

发现范围扩大、冲突或新风险时，停止受影响项并给出更新计划。脚本的--confirm、摘要和日志绑定继续保留，它们是技术校验，不是交互问卷。

## 目录与规则

根据目标目录名、已知任务和现有结构推荐目录。文档任务可只用工作区、参考资料和报告；需要开发或分析时才推荐代码、数据、分析结果等位置；可自由定位的独立环境按需归主项目，已有环境和工具固定位置沿用。没有适用需求的候选不创建，已有工程沿用其原生结构。语言沿用本轮明确选择，未知时先弹窗询问；发现语言差异，前置弹窗确定处理意向，再在计划中列改名建议与风险，不自动改名。

实际新建时，主项目 AGENTS.md 保留规则入口、目标子项目范围和简短文件保护原则，以相对链接引用 PROJECT_RULES.md。项目短规则按“项目约定、目录用途、成果归档、文件保护”组织；未选择成果输出位置时省略成果归档节。只写已选布局及实际用途，目录表可在同一项目内归组；通用候选、中英映射、环境可选类型及详细操作流程留在技能中按需读取。

项目约定保留目录语言、时区和主根环境归属。中文选择覆盖全部自建业务目录层级，工具要求的原生结构保留并说明；此选择不决定文档正文或文件名语言。环境预留只是位置，不代表已安装。可独立归档的报告和分析导出沿用已有约定，尚无约定时在选定位置推荐按日期加用途分组，同次 PPT、对应 PDF 和配套材料共址，同一成果的版本连续递增。源码、设计源文件、关联素材及工具生成目录沿用原生布局，不强套日期或 v01 命名。

弹窗、等待、重发、模拟及对话流程只保留在技能内部，不写入这两份项目规则。没有结构或规则变更时，已有定制 PROJECT_RULES.md 保持原样，不因模板更新自动覆盖、追加通用内容或要求补齐候选目录；新增项目、改变用途或用户要求修订时，在同一计划中按现有内容提出相关差异，保留其余约定。

## 多个独立小项目

主目录下的 wechat、QQ 等独立项目分别管理，以后新增项目继续增量登记，不限定项目数量。主根通常统一维护两份规则文件，不向每个小项目复制同一套规则；已有工程内部规则继续保留。

PROJECT_RULES.md登记各项目的标识、相对根路径、用途和状态，并分别说明文件/配置/数据归属、环境使用范围、成果位置及命名例外。处理一个项目时不套用另一项目的约定，同名文件保持项目身份。集中环境位置不等于项目间共享；共享项另列使用方和维护位置。

新增、改名、归档或改变已登记用途时，完整计划包含对应规则的增量差异；获得该范围的执行指令后一起完成，不再为规则文件重复索取许可。普通内容更新不重写目录规则；手动创建文件夹和只读盘点不会触发后台写入。写后核对登记与磁盘一致，原有项目的专属约定和业务文件不变。完整流程见[多子项目管理](../skills/project-directory-organizer/references/subprojects.md)。

## 首次生成的布局输入

`project_rules.py plan ROOT --language english --timezone TIMEZONE --layout-file -` 从已选布局生成短规则，中文项目将语言参数改为 `chinese`。`--layout-file` 只在首次创建 PROJECT_RULES.md 时必需；助手依据用户已确认的目录计划准备，不增加用户问题或 JSON 表单。`-` 表示经标准输入传入，无需在项目中保存布局文件；也可将该参数替换为已有且获准保存的布局文件路径。

| 字段 | 内容 |
| --- | --- |
| scope | 本项目已知工作范围，使用文字字符串，不要求正式主题名称 |
| directories | 已选目录及用途，格式为 `[{"path":"相对主根路径","purpose":"用途"}]`；用途表允许按类别归组 |
| environment | 本次约定的独立环境目录相对路径，须在 directories 明列；未选择时为 `null`，不表示项目没有已有环境 |
| outputs | 明确选定的报告或导出归档位置相对路径列表，须在 directories 明列；没有则为空列表。不要把 build/dist 等工具生成目录或关联源码素材作为归档位置 |
| originals | 已确认原件的项目相对路径列表，可为目录或文件（如根内 contract.pdf），不要求包含在目录用途表中 |

`TIMEZONE` 替换为已知项目约定或当前会话的时区；没有固定地区默认值。助手从已有上下文取得，不为此增加常规问卷；确实无法确定时先在计划中标为待定，不编造时区。

脚本只有一个environment字段，并保留已有PROJECT_RULES.md，不是多子项目登记/同步器。多个项目具有不同约定或需要增量维护时，助手依照多子项目说明直接准备完整文稿或精确差异，再按已授权范围编辑；keep不代表已登记新项目。

布局是生成输入，不是新增项目隐藏设置。工具计划和摘要不构成写入授权；完整文稿仍先在正式回复中展示，实际写入遵从用户已明确的操作范围。详见[选中布局示例](../skills/project-directory-organizer/references/examples.md)。

## 整理与保护

整理先评估引用、资源完整性、外部依赖、原件、链接及目标冲突。检查通过且独立的完整组可列入移动计划；风险或未知组保留并给建议。代码、环境、原件及项目根改名不作为普通自动整理处理。

本次整理指南MD记录映射、评估、实际结果和回退入口；收到保存或执行指令后，才写入已列明的位置。执行失败停止并保留记录；完整成功且条件满足的移动批次可按明确指令回退。精确删除与恢复仍采用专门流程，不从泛泛整理推断删除。
