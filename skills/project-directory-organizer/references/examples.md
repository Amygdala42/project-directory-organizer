# 目录计划示例

## 前置弹窗与完整计划

用户说“完全重新模拟，主目录是 D:\Projects\示例项目，需要一个资料汇总工作区”时，直接沿用本轮给出的地址，再依次获取尚未明确的操作和目录语言；不从现有名称猜定语言，不继承上轮答案。存在命名差异时先问处理意向，用途不明时补问用途；新建任务的分析目录和独立环境需求分别询问，用户已明确回答的项不重复问。每次一个问题，未答就保留待答状态；消失或超时不代替答案。

假设本轮用户已为当前目标明确采用中文，说明工作只涉及资料阅读和说明文档，代码、运行数据、分析及独立环境分别明确不需要，并希望推荐完整框架；没有其他待确认的选项或约束。此时可在正式回复中推荐以下结构，并补全具体用途、已有/待建状态及规则文稿。示例中的项目和任务名均应替换为用户的实际名称：

```text
示例项目/
├─ AGENTS.md
├─ PROJECT_RULES.md
└─ 资料汇总/
   ├─ 工作区/
   │  ├─ 记录/
   │  ├─ 草稿/
   │  ├─ 素材/         可删减扩展
   │  └─ 审阅/         可删减扩展
   ├─ 参考资料/
   └─ 报告/
```

树内标为待建的目录均属本版拟建范围；可删减扩展说明推荐强度，用户可去掉、合并或改名。若存在未定建议，单独列出，不混入执行范围。到这里结束，不弹窗，不让用户选目录组，也不附加执行确认问题。规则文稿只包含实际目录和文件约定，不复制弹窗或文字反馈流程。英文方案可用对应的 `work/records`、`work/drafts`、`reference`、`reports`。

开发、运行数据和分析成果按各自需求选择；写自动化脚本但不做数据分析时，仍可需要代码和运行数据位置，不据此添加分析结果目录。环境需求单独确认后，新建且可自由定位的环境使用已确认主根的 `env/<项目标识>`，中文业务目录也保留env；既有环境和工具固定位置沿用。已有软件工程沿用其原生结构，不为了套用示例另建一组同用途目录。没有子任务分组需求时，也可把已选业务角色直接放在主项目下；主项目自身的环境仍用 `env/<主项目标识>`。

用户回复“暂时不要报告目录”时修订完整计划再结束；回复“按这个计划创建”才实际创建，不再询问一遍。回复“我先阅读”或仅认可结构时不动文件。模拟计划明确标为模拟，不能因认可模拟而实际创建。

## 语言回答后的连续对话

假设当前主项目及目标位置已明确，目标目录尚不存在，没有命名差异。用户先引用本技能要求“创建一个资料文件夹，生成目录”，但未说明用途；助手已询问目录语言。以下是连续轮次，每行问答完成后才进入下一行，后续回复无需再次引用技能：

| 用户本轮回复 | 助手下一步 |
| --- | --- |
| 英文 | 记录语言，单独询问准备存放什么资料或开展什么工作；不创建。 |
| 保存软件使用资料和说明文档 | 记录用途，询问是否涉及代码；不凭“文档”替用户排除相关需求。 |
| 不需要代码 | 只记录代码需求，单独询问是否采集或处理数据。 |
| 不需要数据 | 只记录数据需求，单独询问是否需要分析成果。 |
| 不需要分析 | 只记录分析需求，单独询问是否需要独立环境。 |
| 不需要环境 | 只记录环境需求；继续检查相关成果、命名、共享或旧约束。需要助手推荐的具体目录名与层级留在框架中展示，不逐目录追问。全部明确后用final展示完整计划及规则文稿，然后结束。 |
| 去掉报告目录 | 修改并重新展示完整计划，然后结束；这是修改意见。 |
| 按这份计划创建 | 核对磁盘状态，在该计划范围内执行，不再询问执行确认。 |

任一待答项未获回复时停留在该项。若用户先前已一次明确提供用途、无需分析和无需环境，这些答案可复用，不能为了凑步骤重新提问；仍需先交付完整计划，再等待针对它的执行指令。

## 从选中布局生成短规则

新建 PROJECT_RULES.md 时，助手把本轮已确认计划转成布局输入，由脚本生成实际约定、目录用途、每次创建前分类、归属与规则维护、文件保护及适用的成果安排。没有选中成果输出位置时省略成果归档节。目录用途可归组，不要求每个叶目录单独占一行；下例规则假设用户已在框架反馈中明确采用，不用JSON替未答事项作决定。规则记录实际路径，不复制全部候选、中英映射和工具操作手册；这些内容按需查[目录参考](directory-reference.md)。

以上中文方案对应的布局示例（路径均相对主项目根）：

```json
{
  "scope": "资料汇总与说明文档",
  "directories": [
    {"path": "资料汇总/工作区", "purpose": "记录存内部来源核对与决策；草稿存未完成正文及编辑素材；保留的审阅子目录存审阅意见；完成的报告与阅读配套放报告目录"},
    {"path": "资料汇总/参考资料", "purpose": "存手册和其他参考原件，保留原件自带的说明与成套附件；自己的阅读笔记放工作区记录，完成的自写报告放报告目录"},
    {"path": "资料汇总/报告", "purpose": "存已完成的说明报告（包括Markdown、PDF或演示稿），及阅读/使用说明、明确交付附件和必要配图；内部记录、草稿、审阅意见与编辑素材放工作区对应位置"}
  ],
  "environment": null,
  "outputs": ["资料汇总/报告"],
  "originals": ["资料汇总/参考资料"],
  "rules": ["报告按内容命名，暂不使用日期子目录或版本后缀；素材与工作稿保留引用关系。"]
}
```

从技能目录运行只读计划命令，并将布局 JSON 经标准输入传入：

```text
python -B scripts/project_rules.py plan ROOT --language chinese --timezone TIMEZONE --layout-file -
```

ROOT替换为实际主项目根，TIMEZONE替换为已知项目约定或当前会话的时区，不使用固定地区默认值。助手从已有上下文取得；确实无法确定时，先在计划中标为待定，不编造时区。主根尚不存在或仅模拟时按模板拟定文稿，不为运行脚本提前创建目录。

也可用 `--layout-file PATH` 读取已获准保存的布局文件。布局由助手依据计划准备，不要求用户填写 JSON、不增加常规问卷，也不为此生成隐藏设置或自动保存临时文件。`environment` 为已选环境的主根相对路径，新建且可自由定位时采用 `env/<项目标识>` 或确有需要的下级环境；基础接口保留旧路径兼容，不用它推导新布局。本次未选环境位置时用 `null`，这不表示项目没有既有环境，也不表示已有目录“尚未配置”。环境和报告/导出归档位置必须在 `directories` 中明列；原件可为根内任一已确认目录或文件，例如contract.pdf，不要求列在目录用途表内或置于某个角色目录之下。目录表归组不会删除创建计划中的子目录，脚本只生成规则文稿，不替代目录创建清单。

布局输入只在首次创建 PROJECT_RULES.md 时必需。没有结构或规则变更时，已有定制规则保持原样，不因与模板不同就追加通用大段内容。新增、改名、归档子项目、改变目录用途或明确采用持续维护时，同一计划包含相应规则差异，保留其他项目约定；具体见[多子项目管理](subprojects.md)和[项目持续维护](project-maintenance.md)。脚本返回keep不代表已完成该合并。AGENTS.md保留项目介绍、已有约束、简短规则入口和文件保护原则，以相对链接引用PROJECT_RULES.md；已采用持续维护时由助手按获准方案补充真实进展与任务入口，脚本不生成这些项目事实。两份规则均不写入弹窗、等待或模拟流程。

## 已采用持续维护的项目

某软件项目已有`src/`和`docs/`，用户明确要求从现在开始记录改动、维护项目进展和按状态归档。沿用现有路径，无需再建一套devlog。下例布局只演示已确认的维护角色，实际方案仍须包括该项目完整的已有目录及必要差异；项目介绍和当前任务由助手根据真实信息补入AGENTS.md，不能以空模板或推测进展代替。

```json
{
  "scope": "软件项目开发与持续维护",
  "directories": [
    {"path": "src", "purpose": "存工程源码与运行所需配套，沿用既有模块和引用关系；工具说明放docs，诊断日志放logs"},
    {"path": "docs", "purpose": "plans存任务与改动记录，notes存调查与决策，tools存工具使用和环境说明；已采用的历史记录按状态归入对应类别下archives，不预建空归档目录"},
    {"path": "logs", "purpose": "存运行与诊断记录，内部草稿和转换中间产物放work/tmp"},
    {"path": "work/tmp", "purpose": "存本次任务可重建的过程文件；重要结果按真实用途另存，临时属性不授权删除"}
  ],
  "environment": null,
  "outputs": [],
  "originals": [],
  "rules": [
    "本项目已采用持续维护，范围为本项目内的实际新建、修改、生成、整理和归档；只读查看与规划不写任务记录。",
    "改动前优先复用docs/plans中的对应任务记录，写明目标、范围与执行步骤；没有对应记录才新建，小改动可只追加几行。",
    "完成后在原任务记录补充结果、实际验证、遗留事项和下一步，并同步AGENTS.md中的简短真实进展和有效任务链接；记录及配套进展入口自身更新不递归创建记录。",
    "笔记使用docs/notes，工具说明使用docs/tools，运行日志使用logs，临时工作使用work/tmp；源码及必要依赖保持工程位置。",
    "已完成、被替代或失效的记录经状态和引用核对后，可归档到所属类别下archives并更新入口；仍有效的旧规范保留维护位置，保留期限不构成删除授权。"
  ]
}
```

该`rules`列表复用现有接口；不添加`maintenance`等未经支持的JSON字段。对于已有PROJECT_RULES.md，基础plan仍可能返回keep，助手应展示并合并获准的精确差异，保留手写介绍和约束。模板升级后重建文稿计划，不复用旧摘要或通过覆盖解决冲突。基础脚本只处理两份规则文件，不创建docs/plans、任务文件或进展内容。

实际收到“修正导出脚本的一处参数”时，先在该任务记录追加目标和准备修改的范围，再改源码并验证，最后回填实际结果和下一步；同一任务的后续修正继续用原记录，不按文件数新建记录。若只是“看看目录是否整齐”，只读检查并回复，不改任务文档。若任务已完成但其设计规范仍有效，可归档已结束的任务记录并更新链接，保留有效规范；不能因日期久远一并搬走或删除。

新建资料库若未采用持续维护，就按其已确认用途创建资料与笔记位置，不添加devlog、logs或任务记录流程。若适用的上层规则已明确覆盖该资料库，则按其范围执行，不能以本地尚未写“采用”为由跳过。用户选择devlog/note、devlog/tasks、devlog/tools也可承载相同角色；若希望临时文件与日志统一放在logs，按实际需要区分其子区并记录用途，不将源码、草稿、缓存和诊断记录无差别混放。

## 已有软件或设计项目

已有 `src`、`tests`、`dist` 或设计源文件与关联素材时，沿用原生结构和引用，不改成日期批次，不给技术文件加 v01 后缀。目录表可以记录这些位置的用途；没有另选独立报告或导出归档位置时，布局使用 `"outputs": []`，生成的项目规则就省略成果归档节。也不因这份示例存在 `reports` 而补建报告目录。

## 已选择日期批次的成果

以下独立示例假设用户已经明确采用“按产出或修订日与用途分组、文件用v01修订”的约定，与上例不使用日期版本的选择分别处理；不因存在报告目录自动套用。

```text
资料汇总/报告/
├─ 20260115使用说明/
│  ├─ 使用说明_v01.pptx
│  ├─ 使用说明_v01.pdf
│  └─ 来源摘要_v01.pdf
└─ 20260115进度汇报/
   ├─ 进度汇报_v01.pptx
   └─ 进度汇报_v01.pdf
```

这里的日期仅用于演示；日常增量归档取项目时区下的产出或修订日。有实际工作或明确预留要求才创建批次，不生成占位文件。同日同一逻辑交付批次复用，同日同用途的独立批次用时间或有意义的序号区分，同成果版本连续。英文批次如 `reports/20260115-user-guide/`，配套文件如 `user-guide_v01.pptx` 和 `user-guide_v01.pdf`。

同一交付批次的PPT在午夜前产出、对应PDF在午夜后完成时，不为日期拆散成套文件；沿用已约定的批次日期口径，在既有记录中说明实际产出时间。另一天的独立修订按既有版本约定保存新增/修订内容。报告的阅读说明、必要配图以及明确要求交付的数据或示例代码可随该报告结构组织；它们混合了格式也不必另建交付目录。只有确需独立打包分发时才安排包的位置，保留必要依赖快照并注明主维护位置，不复制整个内部工作目录充当附件。

## 反复采集、重跑与续跑

某英文自动化项目已选`data/contacts`保存采集资料，明确不设独立报告或分析结果目录；这并不确定它的运行批次方式。先单独确认相关缺项，不自动套日期目录，也不重问已明确的语言和环境。

假设用户随后已明确选择“按开始日、用途及运行序号组织”，data/contacts的主要内容是采集数据，包含联系人JSON和所采事件JSONL；HTML预览用于检查和使用这批数据，作为必要配套。采集器、运行配置、诊断日志和缓存按工程已有位置另存。9点失败的采集与11点独立重跑分别保留，可在完整计划中列出：

```text
data/contacts/
├─ 20260929-contact-export-01/
│  ├─ raw.json
│  ├─ events.jsonl
│  └─ preview.html
└─ 20260929-contact-export-02/
   ├─ raw.json
   ├─ events.jsonl
   └─ preview.html
```

日期、名称和产物仅为已确认选择下的示例，不是必建模板。现有运行记录可说明第一批未完成，第二批是独立重跑；9月30日明确续跑第二批时继续关联`20260929-contact-export-02`并记录实际时间，不把它改名为当天日期。此处events.jsonl是被采集的事件数据；若另一份同后缀文件实际记录程序诊断，则按日志用途放置，不能凭扩展名或同批次共址。也可按角色分开放置并关联同一运行标识；已有脚本固定输出路径时，先检查引用并提出兼容方案，不按本例直接搬迁。

## 日常创建文件

假设现有规则已采用reports存报告成果、images存供复用的图片输出、docs存项目使用文档、src存生成代码、config存运行配置、data存采集或加工数据、work存内部草稿与过程记录、logs存诊断日志；这些不是每个项目必建的目录。一次已授权任务的产物先按项目归属、用途与状态、关联、位置、命名确定如下角色与路径，不能等生成后按后缀整批塞入一个目录：

| 产物及实际角色 | 位置与理由 |
| --- | --- |
| 已完成的summary.md、summary.pdf和slides.pptx | reports/summary/，都是本次报告成果；Markdown不因格式而退回草稿区。 |
| 报告阅读说明README.md、正文引用的chart.png | reports/summary/，帮助读者理解或使用报告的必要配套。 |
| 明确要求随报告交付的results.json、sample.py | reports/summary/attachments/，分别是交付数据和示例代码；说明用途与使用方式，维护源保留在data和src，确需固定交付版本时保存必要快照。 |
| 仍在讨论的summary.md、review.docx和decisions.md | work对应的草稿、审阅与记录位置；与报告相关不使它们成为正式成果。 |
| render.py、settings.json、raw.json、run.log和生成缓存 | 分别沿src、config、data、logs和已约定缓存位置保存；同为JSON的配置、抓取数据和交付附件有不同角色，不能一律叫报告附件。 |
| 供多份材料复用的chart.png、chart.svg及其使用说明README.md | images/对应图组，图片是主要内容，说明记录图例、来源或使用条件；内部生成配置和抓取数据按各自用途另存。 |
| 整个项目的安装与运行说明README.md | docs/，它服务项目整体；文件名与图组或报告的README相同并不改变用途。 |

通过同名、批次标识或文档链接关联分开放置的内容。“同一次运行”“与报告相关”“放在一起方便”都不是归档到同一目录的充分理由。明确要求交付的附件有具体接收用途；中间JSON、内部脚本、审阅DOCX和缓存不能仅改叫“附件”就一并归档。工具只能统一输出时，先在已安排的work/temp生成，再按上述角色选择归档并核对引用；涉及移动时仍按[移动说明](moving.md)处理，受保护代码等不能绕过执行器。

若dashboard本身就是报告，reports/dashboard/可按职责收纳HTML入口、阅读所需JS和图片；生成器及开发配置仍在工程维护位置。若用户另需可独立分发的ZIP交付包，再安排已约定的deliverables等位置，保留必要快照并注明维护源；不因HTML、JS和图片混合就强制另设deliverables。外部收到的ZIP原件仍按来源资料保留，不因相同后缀归入自己的交付物。

资料库已有reference存外部原件、notes存自己的阅读笔记。用户已授权总结一份手册并导出PDF，先读规则，按“本资料库 → 自写笔记 → 与原手册关联 → notes → 已有命名习惯”选路径；检查目标冲突后直接完成，不因PDF后缀放入reference或新建reports，不再询问已确定的语言和环境。

若讨论记录没有适合目录，先核实根目录是否已允许该用途；规则未覆盖时提出最小补充位置及用途，再依授权推进。已有ClientMaterials、WorkingDrafts时可以推荐相同风格的DiscussionNotes，不能因为英文就强制改成小写。新建或导出同样遵守保护与不覆盖规则，批量产物可预先确定对应位置，无需每份写分类日志。

## 风险分流整理

假设某报告目录及全部后代已核实包含正式Markdown、PDF、阅读说明和必要配图，且引用范围与成套性检查充分，可列“检查通过”；不能仅因说明是Markdown就建议移走。另一个目录含内部草稿、生成器、配置和运行日志，不能整目录移入reports；用途不匹配不能列clear，生成器等还受执行器保护。脚本引用中的图像列“有风险”；无法核实外部引用或文件实际角色的内容列“无法确认”。关联组不拆开绕过阻止，含受保护对象的整组仍按工具限制保留。

正式回复完整列出原→新映射、阻止项理由、回退方法及指南/计划/日志路径，然后结束。用户明确说“执行上述通过项的移动”后，按[移动说明](moving.md)执行，风险和未知项仍保留。只有建议或全部不可移动时不写指南；用户明确要求保存方案时才保存。
