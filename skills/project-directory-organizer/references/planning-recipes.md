# 可裁剪的规划范例

用于用途已经明确、需要目录建议时。先考虑用户以后怎样找文件，再选择主要分类维度：按项目找、按工作阶段找，或按来源/主题找。按“项目归属 → 用途与状态 → 关联 → 位置 → 命名”选择结构；文件后缀不是用途。

以下角色用于组合第一版框架，可在相关范围内适当多列工作环节，标注建议保留或可删减扩展并说明用途。用户删减后重列完整方案，明确拟建范围后再执行；范例本身不授权创建，也不增加逐目录问卷。沿用本项目已确认的语言、代码/运行数据/分析需求、环境、成果与共享安排；只补问尚未明确且相关的需求；目录的具体名称与层级可先推荐。不从“资料库”推断没有代码或分析需求，不从“项目交付”推断必须有环境或期限。已选英文目录不决定正文语言。

| 场景 | 适用的找文件方式 | 候选角色（英文 / 中文） | 裁剪要点 |
| --- | --- | --- | --- |
| 内容创作 | 按选题、制作批次和发布状态找材料 | topics / 选题、assets / 素材、work / 工作区、deliverables / 成品 | 初稿可覆盖选题、草稿、素材、审阅和发布，用户可合并或删减；分析复盘仅在实际需要时增加。成套素材与工程文件保持关联，不把制作工程拆成扩展名分类。 |
| 项目交付 | 按任务、交付批次及决策找材料 | reference / 参考资料、work / 工作区、deliverables / 交付物、records / 记录 | 初稿可列参考、工作、审阅、交付和记录等相关环节；日期批次另按需要选择。报告与阅读配套、明确交付附件按实际交付职责组织；已有reports能承载时不因混合格式另建deliverables。独立打包确有需要时再安排位置；维护源码、锁文件和构建结构沿原位置。 |
| 资料库 | 按主题、来源和自己的笔记找材料 | reference / 参考资料、notes / 笔记、inbox / 收件箱 | 需要接收流程时可把收件箱作为可删减扩展；归属不明的既有文件留在原位，不自动移入。资料原件保持来源状态，笔记与加工副本分开。 |

每个采用目录都写清职责、主要内容、必要配套及应另存内容的去向，覆盖参考、笔记、素材、数据、代码和工作记录等所有实际角色。必要配套服务于理解、使用或明确交付；同一运行或相关任务不构成共址理由。生成前为产物分配角色和路径；统一输出工具先在已安排的work/temp等工作或临时位置生成，再选择归档。项目已有格式限制仍保留，旧文稿和文件不因范例变化自动迁移。

不强制数字前缀、统一日期层级、固定目录数量，也不把目录范例作为 `directory_verify.py` 的要求。可检查规则只能来自实际采用的约定。

## 示例：英文资料库，无独立环境和报告目录

假设用户已确认只需要来源资料和自写笔记，且明确不需要代码、运行数据、分析成果、独立环境或报告目录，则候选可精简为：

```text
manuals/
├─ reference/      来源手册原件
├─ notes/          自写阅读笔记
├─ AGENTS.md       规则入口（独立主项目时）
└─ PROJECT_RULES.md
```

若 manuals 是已有主项目下的子项目，使用主根登记和现有入口，不复制两份主规则到 manuals。无新接收流程时不加 inbox；已存手册不因范例改名或移动。

供现有 `project_rules.py plan` 使用的已选布局示例：

```json
{
  "scope": "来源手册与自写阅读笔记",
  "directories": [
    {"path": "reference", "purpose": "存来源手册原件及其自带的说明和成套附件；自己的笔记放notes，不改写来源原件"},
    {"path": "notes", "purpose": "存自写阅读笔记及理解笔记所需的配图；来源手册原件及其附件放reference并保持引用"}
  ],
  "environment": null,
  "outputs": [],
  "originals": ["reference"]
}
```

布局是助手根据确认结果整理的生成输入，不要求用户手填 JSON。实际主根不存在时直接展示计划，不为运行脚本提前创建。原件路径来自实际用途确认，不从目录名反向猜测。完整计划和既有明确执行指令的衔接仍按[操作说明](operations.md)进行。
