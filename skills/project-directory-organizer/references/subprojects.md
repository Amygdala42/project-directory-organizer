# 多个独立子项目

当用户在同一主目录管理多个独立小项目，或继续新增小项目时使用本页。项目数量没有固定限制；软件名称只是示例，不据名称推断用途、环境或授权。

## 范围与归属

- 主项目根保存总规则；子项目根界定一次具体工作的文件范围。根据用户指向、现有登记及任务上下文确定目标，不能把当前工作目录在主根理解为可修改所有子项目。
- 文件身份包括所属子项目和完整相对路径。不同项目的同名脚本、配置、联系人导出、日志或报告分别保留，不能只按名称、扩展名或内容相同跨项目合并。
- 配置、数据、凭据引用、业务依赖、日志、输出和归档批次分别归属各项目。修改一个项目，不把它的命名、环境或成果规则套到其他项目。凭据只记录变量名或获取方式，不写值。
- 同一任务明确涉及多个项目时，分别列出各自的操作及共同影响。目标或文件归属有歧义时先澄清；已从上下文明确的范围不重复询问。
- 共享资源另行登记适用项目、维护位置和必要的版本约束。集中放在主根不等于共享；改动共享资源时评估所有登记使用方。已有原生工程、环境及子目录AGENTS.md沿用，不移动、覆盖或复制一套新规则代替它们。

## 总规则的内容

默认只在主根维护AGENTS.md与PROJECT_RULES.md，不为每个小项目复制相同规则。AGENTS.md要求先读总规则并确定本次目标；PROJECT_RULES.md由以下内容组成：

1. **公共约定**：主根、路径基准、已确认命名的适用范围与时区、项目隔离、共享边界和文件保护。主根的一般语言约定不替未登记的新项目作出语言选择。
2. **子项目登记**：每项包含项目标识、主根内相对路径、用途、状态。可沿用现有集中表；脚本生成时将每个项目的登记字段和专属规则放在同一独立段，避免另建一份重复登记表。状态区分实际存在、计划待建、已归档或待核实；不能将已存在目录写成已安装环境。
3. **各子项目规则**：按项目分别列目录/文件用途、配置与数据归属、环境位置及使用范围、已采用的成果位置与命名例外。所有路径以主根为基准。没有独立环境、没有独立报告目录也应按实际说明；不强建相同骨架。
4. **共享项**：只列已确认共享的资源、位置及使用方；无共享约定则说明目前未约定，不创建共享目录。

持续采集或自动化任务已确认运行批次方式时，在该项目的对应数据/记录用途中注明独立执行、重跑、续跑和跨日归属；没有独立报告目录不等于没有运行产物。新增运行批次不算新增独立子项目，沿用已明确的项目选择，只补齐与本次工作有关的未定约定。

这些字段由已有规则和本次确认结果整理，不增加一轮整表填写或重复问卷。新增独立项目重新检查全部前置选项及会影响本次工作的已有约束，包括语言、用途、分析、环境、成果位置、命名归档和共享资源；只复用明确覆盖当前目标的答案。甲项目的“英文”“不需要”“无报告”“共享环境”等不替乙项目作答。用户明确为本次多个目标给出相同选择时可一并记录；其他未明确项按目标逐个询问。未知项不能从主根概括性约定或相邻项目抄填，也不能先填进计划等用户纠正。

## 新增及后续维护

| 触发情况 | 规则文件处理 |
| --- | --- |
| 新增、改名、归档子项目，或改变已登记用途/位置 | 在同一完整计划中列出登记表和受影响条款的精确差异；按已获执行指令同步写入。 |
| 已授权的新增/整理任务明确包含上述目录和规则变更 | 连同规则完成，不把写.md变成新的确认门槛；保留所有未涉及项目约定。 |
| 普通内容编辑、保存已登记位置下的新成果 | 沿用所属项目规则；没有改变约定就不重写总规则。 |
| 用户手动新增目录后请求纳入管理 | 核实用途与归属，再按此次要求规划/登记；不从目录存在推断其已配置或可共享。 |
| 只读盘点、假设、模拟或仅询问会不会更新 | 只说明现状和差异，不写文件、不启动目录监听或计划任务。 |

新增项目通常只增加登记行与专属小节；公共规则有变化时说明影响范围。AGENTS.md入口已经满足要求时保持不变；不因为每次新增项目就重复追加入口。跨项目改名、移动和删除仍遵循各自的风险检查与授权范围，归档状态更新本身不授权移动或删除。

**脚本边界：** `project_rules.py plan` 保留基础文稿接口；它对已有PROJECT_RULES.md返回keep，不代表已经登记新项目。已有总规则的增量维护使用下面的 `update-plan`，每项目分别提供环境和成果位置。两种计划都由 `apply` 执行；不为绕过keep删除旧规则，不把基础布局的单一environment误写成所有项目共用。

若现有文档没有登记表，只补充当前相关项目的登记，原有专属小节原文保留。不在当前任务范围、无法核实的条目保持原样，在报告中说明待核实；不顺便改造其他项目。不要用通用模板替换已有全文。

## 增量计划接口

主根必须已存在且包含UTF-8编码的PROJECT_RULES.md。输入仅整理当前目标已经确认的事实，不能用JSON默认值替用户回答未知问题。示例 `projects.json`：

```json
{
  "projects": [
    {
      "id": "telegram",
      "path": "telegram",
      "purpose": "Telegram软件手册整理",
      "status": "planned",
      "language": "english",
      "environment": null,
      "outputs": [],
      "rules": ["资料保存在telegram/reference；原始手册名称保持不变。"]
    }
  ]
}
```

- `id` 为稳定标识：1至64个ASCII字母、数字、下划线或连字符，首字符为字母或数字；不能重复或仅大小写不同。修改用途、路径或状态沿用原id。
- `path` 是完整主根相对路径；独立项目根不得重叠、包含其他登记项目。`status` 只接受 `planned`、`active`、`archived`，表示明确确认的计划、实际存在或归档状态；脚本不据此声称目录或环境已经创建。
- `language` 只接受 `chinese` 或 `english`，记录目录语言。`environment` 为明确无独立环境时的null或完整主根相对路径；`outputs` 为已选成果路径列表，可明确为空。环境和成果必须严格位于该项目根之内，不能跨项目；环境位置与任何成果位置不能重叠或互相包含。成果路径之间可以包含，但不能重复登记同一路径。共享资源仍由人工单独登记，不猜测共用关系。
- `purpose`、`rules` 中各项必须是非空单行文本；标记注入和控制字符拒绝，Markdown特殊字符转义。规则按确认结果完整列出，更新目标段时替换该项目原生成规则；没有传入的其他项目保持原字节。
- 本接口不新建、改名、移动或删除业务目录，不安装环境，不删除项目登记。`archived` 仅更新状态；实际归档操作需另有范围与计划。

```text
python -B scripts/project_rules.py update-plan ROOT --projects-file projects.json
python -B scripts/project_rules.py apply ROOT --plan-file reviewed-plan.json --confirmed-plan-digest SHA256
```

`--projects-file -` 和 `--plan-file -` 接受stdin，不要求在项目中保存计划或隐藏配置。`update-plan` 只读；它输出schema 3、完整上下文的 `diff`、目标文件快照、最终内容摘要及 `plan_digest`。已确认的全部目录/文件操作及这份差异仍须纳入同一完整计划。获得该计划的执行指令后调用apply；摘要校验不是用户授权，也不是新增确认题。

执行前重新计算整个计划，核对主根身份、文件身份、mtime、内容摘要及记录；不接受陈旧或被篡改的计划。写入复用操作系统文件锁和写后摘要核验。已有schema 2基础计划和原CLI保持兼容。写入不是跨文件事务；中断或出现 `started_writes` 时先检查文件，再生成新计划，不盲目重试旧计划。

### 首次纳管与旧文档迁移

每个项目只维护一对明确id的HTML注释标记。起始标记记录项目根及原生成正文的SHA-256，结束标记重复id；正文、换行或标记被手工改动时保留现场，返回blockers。标记重复、损坏、嵌套、位于代码围栏/缩进代码内，或现有登记不明确，也不写入。不要为了让检查通过而手工重算标记摘要。

没有管理标记的旧文档默认返回 `manual_merge_required`，不会自行追加第二套登记。允许以下明确入口：

1. **迁移已存在的单个项目段**：在该项目记录中增加 `before`，值为旧文档中该项目完整段的精确文本（包含真实换行符）。该文本必须唯一、处于完整行边界且在代码围栏外，不得含其他管理标记或覆盖整个文档；只替换这一段并加入管理标记。多个before不能重叠。原文有集中登记表、其他同id/路径引用或重复项目条目时需人工审查精确差异，不能留下双重登记后直接纳管。
2. **尚无项目登记时初始化首个区**：确认旧文档没有项目登记冲突后，在顶层增加 `initialize_after`，值为唯一出现、在围栏外、以换行结束的精确已有文本锚点。插入点在该文本之后，旧锚点及其他所有字节原样保留。例如实际文档首行为 `# 项目规则\n` 时可指定 `"initialize_after": "# 项目规则\n"`；CRLF文档必须使用实际 `\r\n`。空文件可显式传空字符串。不得与已有管理区或before迁移混用。检测到未纳管登记标题或目标id/路径引用时仍返回blockers，不能用该参数绕过迁移。

完成首次纳管后，新项目只需传自己的记录，会紧接最后一个管理段插入；已有项目按稳定id原位更新。重复生成相同记录得到keep和空diff。迁移与新增混合时先完成迁移，再为新增项目生成新计划。超出精确自动合并能力的旧集中表或人工段继续按本页准备人工合并差异，不据此重写全文。

## 写后核验

实际执行后逐项核对：登记路径与磁盘一致；用途及状态准确；AGENTS.md相对链接可达；新项目的环境和成果规则与已确认选择一致；原有项目的专属条款和业务文件保持不变。针对跨项目隔离，可对原有配置、数据和代表性输出比较前后内容摘要；不能只凭文件名判断无误。

重复执行同一已完成任务不得重复登记、重复追加规则或覆盖文件。若文件或目录发生并发变更，只停止受影响部分并报告差异。说明这次实际维护了哪些规则；不得声称后台持续同步。

## 示例：两项工作增加为三项

假设用户已确认wechat用于微信自动化、QQ用于QQ工具研究，后来新增telegram用于软件手册整理；目录名大小写均保留。本例中，用户已明确为telegram选择英文目录，还分别回答不需要分析目录、不需要独立环境，并选定资料位置。若仅知道用途，仍须先确认该项目的语言，再依次询问分析和环境，不能直接套用主根约定或本例的选择。总规则可登记为：

| 项目标识 | 相对根路径 | 用途 | 状态 |
| --- | --- | --- | --- |
| wechat | wechat/ | 微信自动化研究 | 已存在 |
| QQ | QQ/ | QQ工具研究 | 已存在 |
| telegram | telegram/ | Telegram软件手册整理 | 计划待建；执行后核实更新 |

若已有wechat/.venv和wechat/reports，QQ使用系统Node.js与QQ/exports，应原样保留；按上述已确认选择，只为Telegram规划已选的资料位置，不复制微信的环境或QQ的导出规则。wechat/config/settings.json和QQ/config/settings.json是两份独立配置。

新增Telegram时，计划同时给出它的登记行和专属规则差异，执行后把实际创建成功的状态改为已存在。未来新增第四、第五个项目沿用同样的增量登记方式；不会预建未知项目或自动为所有项目安装相同工具。
