# 项目持续维护

用于将项目上下文、变更记录和历史归档纳入已经采用的目录规则。沿用“归属 → 用途与状态 → 关联 → 位置 → 命名”，不按后缀切分项目，也不替代工程自身的开发、测试或发布流程。

## 采用与适用范围

用户或适用的已有规则明确采用时执行；已有授权和覆盖范围直接沿用，不重复提问。不从项目大小、出现AGENTS.md或某个devlog目录推断已采用。未采用时不新增记录义务，也不为一次只读盘点推荐整套管理框架。规划新项目时，可按实际维护需要提出此方案，将采用范围和具体位置列入完整方案，收到执行指令后再落盘。

项目规则须写明：哪些项目采用、任务记录和当前状态入口在哪里、笔记与工具说明如何归属、日志与临时工作位置、归档条件及路径。可以记录明确适用于当前项目的上层约定，无需将全局原文复制到每个项目。目录没有实际用途时不预建；已有约定充分时复用，不要求用户逐字段填写。

## 分层入口与事实

| 位置 | 维护职责 |
| --- | --- |
| 适用的全局AGENTS.md | 通用工作流、护栏及常用Skill入口。项目任务只遵守适用内容；没有单独授权不修改全局文件、不扩大到其他项目。不要复制整份技能正文或维护一套重复的全量索引。 |
| 项目AGENTS.md | 简短项目介绍、关键约束、PROJECT_RULES.md入口。采用持续维护后保留当前阶段、更新时间、当前任务链接和必要的下一步；只写已核实事实。 |
| PROJECT_RULES.md | 项目目录与维护流程的主约定，记录角色、具体位置、范围及归档条件；状态事实和详细执行历史不重复维护在这里。 |
| 任务记录 | 一项任务的目标、范围、计划、重要决策、执行结果、验证、遗留及下一步，是详细进展的维护位置。 |

已有项目介绍、手写约束、下级AGENTS.md及有效链接保留，只增补相关差异。项目AGENTS.md不扩成长篇日志；已有README承担介绍时可引用。当前阶段无法核实时注明待核实，不把上月进展改日期后当作新进展，也不把新计划写成已完成。多项目入口只汇总明确涉及的项目，不更新无关项目状态。

## 改动前与完成后

1. 开始时读取适用入口、项目规则和当前任务记录，核对任务范围及实际状态。纯只读查看、核对、询问或假设讨论不创建、更新记录或进展；用户明确要求保存检查报告时，该保存属于已授权写入。
2. 进入已授权实际改动前，先复用或创建本任务记录，至少写目标、范围、准备改什么和如何验证。小改动可在现有条目追加几行，多步变更补充步骤及必要回退办法。同一任务不按每个文件另建文档。
3. 按规则创建、修改、生成、整理或归档，重要范围变化与决策更新到同一记录。任务记录自身的创建、修订、回填和归档使用原记录承载，不递归创建“记录记录的记录”。规则维护本身也是任务，可记录于既有合适位置；新项目先在对话计划中列明记录位置，执行时先建立必要位置及记录，再开展其余业务变更。
4. 完成后回填实际变更、验证结果及范围、失败或未核实事项、遗留和下一步，并更新项目AGENTS.md中的简短状态和任务链接。未通过验证不得标为成功；中断时保留进行中/受阻状态。当前任务已完成但仍是当前版本的追溯入口时可留在原位置，待退出当前维护范围再评估归档。

已采用的项目中，授权业务改动包含规则明确要求的必要任务记录和状态回填，无需为同一记录再次索取许可；不据此扩展业务范围。尚在目录规划、仅讨论建议或未授权写入时，先在对话里展示方案，不以“先记文档”为由提前创建文件。记录路径缺失时只补充当前任务所需的路径与规则；归属冲突或可能覆盖既有内容时停止受影响项并核实。

## 记录角色与可选布局

| 角色 | 可选位置 | 内容边界 |
| --- | --- | --- |
| 笔记与决策 | devlog/note 或已有notes/docs位置 | 调查、想法、讨论及决策依据；稳定知识在一个明确维护位置保存，其他文档链接引用。 |
| 任务 | devlog/tasks 或已有plans/tasks位置 | 目标、计划、执行与验证记录；不混入原始运行输出或最终交付物。 |
| 工具说明 | devlog/tools 或已有docs位置 | 工具用途、版本条件、命令和维护说明；可含必要示例，长期工具源码、配置、锁文件及依赖沿工程位置保持关联。 |
| 运行记录 | logs 或已有记录位置 | 执行日志、诊断证据及必要说明，重要结论提炼到任务或笔记并指向证据；不把所有同次生成文件都归入日志。 |
| 临时工作 | 已约定的work/tmp、logs/tmp或工具固定位置 | 转换中间件、一次性生成器与缓存等，按实际角色和工具限制保存；正式成果与长期维护源另有位置。 |
| 历史归档 | 各分类下archives或已有历史位置 | 已退出当前维护范围的记录和被替代说明，保留状态、关联和来源。按需要建立，不能只因示例出现就预建空目录。 |

note/tasks/tools是用途选项，不是扩展名类别。各角色可以共用一个已约定的小型文档目录，通过文件名或章节区分；复杂项目才增加层级。用户已将日志和暂存统一放在logs下时，明确子区或文件组职责及各自保留需要，不为名称整齐拆散引用。

## 归档与清理

先核实记录已完成、被替代、取消或失效，以及是否仍承担当前入口或有效规范。旧但有效的规范继续维护；日期、最大编号或修改时间均不能独自证明状态。归档可在原记录中注明状态、完成时间及替代文档，不要求为每次归档再建一份索引。

实际移动需要明确原→新映射、目标职责、引用与依赖检查及本次操作授权，遵循[移动流程](moving.md)。更新受影响的AGENTS入口、任务索引和文档链接；归档状态不等于已经搬移。不能安全修改的外部引用须报告并保留相关材料原位。已有历史不因新版目录建议整批迁移，不将未知或仍有效材料按“旧文件”处理。

日志和临时文件可以记录保留期限、清理条件及仍需复现的内容。期限到达仅产生待评估项，不是自动删除授权；精确删除与恢复仍遵循[安全删除](safe-deletion.md)。日志和归档也不替代备份。

## 生成、旧项目升级与核对

采用范围和具体角色路径使用现有布局的rules条目表达，与directories的实际用途保持一致；不新增schema字段。完整布局例子见[已采用持续维护的项目](examples.md#已采用持续维护的项目)。生成模板提供条件式维护条款，只有用户或适用规则明确采用时生效，不能从模板条款的存在反推已采用。

基础project_rules.py只生成或保守维护AGENTS.md、PROJECT_RULES.md，不自动创建devlog或任务记录，也不自动维护当前进度。采用后，助手还须按已经批准的方案补齐真实项目介绍、任务记录及AGENTS状态链接，核实必要目录和规则一致。受管规则段之外保留项目事实；更新事实不改写受管标记或覆盖手写内容。

升级技能和安装副本不会更新任意旧项目。用户明确要求纳管或同步指定项目时，读取原文，核对实际缺项，以精确差异合并项目规则、必要入口和角色映射。已有规则冲突需按本次授权处理，不使用新模板全量替换；无需改动时保留原文。基础plan对旧PROJECT_RULES.md返回keep只是保留，不能报告为已同步；受管段冲突须审核合并，不能重复追加。模板变化后重新生成旧计划并核对，不能绕过plan_changed保护。

执行后分别报告：技能和安装副本是否更新、哪些项目实际采用了流程、哪些旧项目未纳入、任务记录与状态是否回填，以及验证范围。文件、链接和显式约定可以由现有工具辅助核对；任务记录是否先于变更、状态是否真实、归档是否合适仍需结合实际执行证据人工判断，不将directory_verify.py描述为新增语义检查器。项目规则指导助手执行，不监听手工操作或拦截其他程序输出。
