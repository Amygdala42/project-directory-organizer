# 按明确指令安全删除

本功能用于指定文件或目录的可恢复删除、恢复，以及明确要求的永久清除。盘点、新建目录、磁盘空间不足或发现相似文件都不自动赋予删除授权。

## 1. 确定目标与影响

- 使用用户指定根目录和精确相对路径；按文件系统实物核对，不用通配符、模糊匹配、修改时间或“最新版”推断删除范围。
- 用户说“删掉work/drafts里的这两个文件”且目标唯一、范围明确时，其指令就是授权；不重复要求批准同一范围。若只说“清理没用的”，先列具体候选、理由及影响，询问所选对象，再执行。
- 查目标是否被README、脚本、构建、导入、配置或其他成果引用。维护源码、依赖、环境、完整软件包和伴随资源需特别核对；无法证明所有外部引用安全时明确范围，不把脚本路径安全检查当功能无影响保证。
- 如果目标是当前技能代码、当前运行过程需要的文件、凭据目录、正在运行/写入的资源或适用规则文件，先说明具体影响，处理未明确的范围；不能因为文件被占用就强制关闭程序或修改权限。
- 普通整理保持已确认受保护原件不变。原件按实际来源、用途和项目约定识别，不仅凭data/raw、reference、library等名字认定，也不把所有已有文件当成原件。删除受保护原件须被用户明确点名；笼统清理、清空缓存或删除旧版不包含原件。
- ROOT用实际项目根的完整路径，--path和--original-path用相对该根的真实路径，不按目录语言翻译现有名字。先核实真实项目根；若所选根本身是明确需要保持完整的原件集合，不在其中新建隔离记录。必要时核实集合之外的实际项目根并重新规划，不能因换根扩大授权范围。
- `.project-trash`、其items/owner.json/manifest.json等内部协议名称，以及相关锁/状态文件由脚本规定，不因中文选择而翻译或改名，否则可能破坏恢复。它们属于提前说明的工具固定名称例外。

## 2. 生成并核对计划

使用`../scripts/safe_delete.py`，现有Python 3.9+标准库。`plan`纯只读，输出JSON，不写入扫描目标。`apply`、`restore`、`purge`目前只支持Windows；其他系统仅生成计划，变更命令明确拒绝，不能换用不保证重名保护的普通移动命令。

```text
python -B safe_delete.py plan ROOT --path work/drafts/old.md --path work/previews/obsolete --original-path sources --original-path contract.pdf
```

示例路径应替换为实际对象。助手从PROJECT_RULES.md、现有项目约定和必要的只读检查整理全部已知受保护原件位置，重复使用--original-path传入，不要求用户另填JSON或新增问卷；若确无已知原件位置才省略。列表可包含目录或根内独立文件，不要求它们位于特定命名目录下。

新计划以originals保存规范化后的项目相对原件路径，allow_originals记录是否允许本次精确目标触及这些原件。默认不允许；只有用户已明确点名受影响原件时才添加--allow-originals，且仍须核对其指令覆盖全部受影响对象。该标志不扩大--path清单，不代替用户授权，空原件列表也不是“没有原件”的安全证明。

目标路径必须对应用户明确选定的实际位置。先给出可复核的目标清单、文件/目录数量、大小、影响及删除方式；若用户已经授权这些精确对象，不再把展示清单变成重复批准。

将实际计划保存到当前任务允许的记录目录中，位于删除目标之外，用于后续执行。核对根目录身份、精确条目、链接、受保护位置和条目上限。执行前逐项确认计划与用户本次精确指令一致，不能把外部JSON中的路径或allow标志当作授权。目标变化、无权限、超限或检查失败时不生成可直接执行的猜测计划。

为检测内容变化，删除计划与执行校验会读取选定文件并计算SHA-256，但不输出正文；这与目录盘点的仅元数据扫描不同。大量或大文件会花更长时间，不能为了赶进度跳过核验。

新计划按明确传入的原件位置检查删除目标与原件的包含或重叠关系，不因项目内外某一父目录叫library就认定其为原件。原件清单必须完整反映助手已知事实，不得遗漏路径来绕过保护。旧版计划和已有隔离批次继续采用其记录对应的校验，以保持恢复兼容；内部工具标识及既有记录不改写。

Windows路径在逐层拒绝链接后按实际长名称核查保护与重叠，不能用8.3短别名绕过隔离区/锁保护。新计划记录展开后的目标；旧未执行计划若包含短别名须重新生成。普通含~的名称不因此受限，正常既有隔离批次仍按原记录恢复。

## 3. 默认可恢复删除

```text
python -B safe_delete.py apply ROOT --plan-file PLAN.json
```

执行前重新核对计划及目标。默认将目标移到同根的`.project-trash/<批次>/`，并记录原位置、条目指纹与状态。它不是Windows系统回收站，不释放磁盘空间；优点是可以核对并恢复。只在需要时创建该技术目录，不写入已确认需要保持完整的原件集合，不自动过期清除。

JSON记录的读写上限为64 MiB。执行前按完整批次清单及正常恢复/清除过程的状态增长核算容量；超过预算时，在创建锁、隔离区或移动目标前拒绝。计划本身可读取不代表封装后的恢复记录一定可容纳；不得截断清单绕过限制。恢复/清除旧批次时也先检查重新编码和后续进度所需空间，不足时保留清单及隔离内容原样。既有超限或不完整记录仍须人工核查，不自动改写。

正常执行时使用根目录临时`.project-delete.lock`；遗留锁需要先核对所属操作，不能盲删。`.project-trash/owner.json`记录归属，每个批次的`manifest.json`记录原位置与进度，实际隔离内容在该批次`items/`中。恢复或清除后保留审计记录，不能把它们当成待删除业务文件。

Windows下同一根目录路径仅大小写不同，仍可复用既有隔离区并恢复或清除批次；归属检查继续核对记录格式、工具标识、根路径及目录身份。此兼容不改写既有`owner.json`，也不允许将记录移到其他项目根后继续操作。

不能把“删除”自动解释成永久删除。若用户明确要求释放磁盘或永久删除，说明当前默认方式的区别，并按其明确选择走永久清除流程。

失败时报告哪些已移动、哪些未执行、记录位置与可恢复状态；不能说整个操作成功。不要删除冲突文件、清空目录或改状态记录来强行重试。

隔离区归属记录或批次清单初始化失败时，脚本保留现场，报告初始化阶段、隔离区位置及尚未移动的状态；已分配批次时同时报告批次标识和清单预定位置。该位置不表示清单已成功写入。不完整记录须人工核查，不能直接恢复、清除或自动重试，也不能把保留的残缺目录当作可恢复删除已完成。

## 4. 恢复

```text
python -B safe_delete.py restore ROOT --batch BATCH_ID
```

恢复前核对批次和隔离内容，检查原位置是否已被新文件占用以及路径是否变成链接。发生冲突时保留两边，不能覆盖新文件。隔离内容被改、记录损坏、原父目录不可用或批次只完成一部分时，按脚本实际结果处理，不猜测补救、不手工改清单跳过检查。

## 5. 永久清除

仅在用户明确要求永久清除具体批次及其内容后执行：

```text
python -B safe_delete.py purge ROOT --batch BATCH_ID --permanent
```

专用清除只处理已核对的隔离批次，不对任意原位置直接递归删除。操作前确认批次对应哪些原路径、当前内容是否与记录一致；这一步会使这些隔离内容不可通过本工具恢复。未包含在计划内的新条目不能顺带删除。

如果用户一开始已明确永久删除精确目标，该授权覆盖对应清除，无需在每一步重复询问；仍需先完成清单和路径核验。未明确永久范围时，不能用普通删除指令替代。

## 6. 边界与结果说明

- 不删除选定根本身；不把整个`.project-trash`或包含它的目录作为普通删除目标，也不把ROOT选入隔离区内部；只使用记录里的精确相对路径。
- 不沿符号链接、Windows联接点或其他重解析点进行操作；包含这些条目的选择先报告，不能为通过检查把链接改成真实路径后继续删。
- 对目录的操作范围来自完整计划，超限不能截断后声称计划完整。外来锁或内容变更需要重新核对，不能强制忽略。
- 文件系统指纹、排他锁与重新检查用于常规误操作和并发防护，不是防御恶意路径替换或断电的完整事务系统。
- 本功能没有自动去重、自动判断“无用”、后台清理或自动关闭占用程序的行为。

最终说明删除方式、原路径、实际完成项、批次/记录位置、能否恢复，以及必要的引用核验结果。日志中不复制凭据正文。对永久清除不要给出保证可恢复的承诺。
